# VisualUnified SDN Control Center — Phase 2

Implemented and checked on Windows, 2026-11-10. These are **simulated logical
rules and packet outcomes**, not OVS flow entries, OpenFlow messages, switch
statistics or real network measurements. Original methodology files and policy
helpers were not changed. Phase 1 mobility, SUMO adapter and map controls remain.

## Rule schema and synthetic packets

Old saved rules remain valid. Missing new fields default to wildcards. Configured
rules stay in `controller_settings.json` with the existing `config`/`rules`
structure. IDs are generated by the controller and cannot target internal rule
names. Flow counters, reputation, detection state and timeline are not writable
rule properties and are not persisted as configuration.

| Field | Accepted value / default |
|---|---|
| `id` | Controller-owned stable ID, e.g. `rule-1`; omitted on create |
| `label` | Up to 80 characters; `Custom rule` default |
| `priority` | Integer 1–999; default 500; local to static selection |
| `source`, `destination` | `*`, V01–V12, or RSU-1–RSU-3; default `*` |
| `source_ip`, `destination_ip` | Exact IPv4 address or `*`; default `*`; no CIDR |
| `protocol` | `*`, `UDP`, `TCP`, `ICMP`; default `*` |
| `src_port`, `dst_port` | Integer 0–65535 or null/blank/`*` for any; no ports with ICMP |
| `traffic` | `*`, `UDP_FLOOD`, `SAFETY`, `TELEMETRY`, `BEACON` |
| `rsu` | `*` or RSU-1–RSU-3; default `*`; source-side ingress association |
| `action` | `ALLOW`, `DROP`, `METER`; default `DROP` |
| `rate_kbps` | Integer 10–50000 for METER; otherwise null |
| `enabled` | Boolean; default true |

V01–V12 map to **synthetic** 10.0.0.1–10.0.0.12, and RSU-1–3 to 10.0.1.1–3.
This is the dashboard's metadata scheme; it does not reinterpret station roles
or addresses in the original Mininet methodologies. Offered packets are UDP:
safety destination 5005, flood/data 9999, telemetry 9000, beacon 9001. Vehicle
source ports are `40000 + vehicle number`; RSU source port is 9001. These fields
never open sockets. TCP/ICMP matching is available only for hypothetical previews;
the runner does not fabricate TCP/ICMP offered traffic.

Example rule (POST `/api/rules`):

```json
{
  "label": "Victim UDP cap", "source": "V07", "destination": "V02",
  "source_ip": "10.0.0.7", "destination_ip": "10.0.0.2",
  "protocol": "UDP", "src_port": 40007, "dst_port": 9999,
  "traffic": "UDP_FLOOD", "rsu": "*", "priority": 800,
  "action": "METER", "rate_kbps": 500, "enabled": true
}
```

Edits are complete rule replacements; omitted optional match fields become
wildcards. The editor sends all its fields. Invalid/nonintegral priorities,
rates, ports, addresses and protected properties return HTTP 400. At most 100
configured rules are accepted. Updating/toggling a rule starts a new counter
revision and clears only that rule's M1 token budget; deleting does the same.
M2/M3 state, counters, budgets and unrelated configured policies are retained.

## Execution and priority

1. With M1 enabled, select the highest-priority matching configured rule. Ties
   use ascending rule-ID text order, e.g. `rule-10` before `rule-2`. User rules
   and the original example static rule share this existing M1 enable gate.
2. Selected static DROP wins and prevents M2 observing that packet.
3. Otherwise, victim-bound monitored UDP is observed by the original M2 helper.
   An active temporary M2 block wins over forwarding and all meters. Stage 1
   remains 500 kbps with the original dwell/expiry semantics and 30 s Stage 2.
4. Applicable static, M2 and M3 meter budgets are independent. Every applicable
   budget must admit the packet; admission debits all of them. If any is empty,
   no budget is debited and the packet is rate-limited. The strictest configured
   rate is displayed, but a different budget can be exhausted first because
   its traffic scope/history differs. The actual record identifies that owner.
5. Normal forwarding proceeds to modeled route, radio and congestion outcomes.
   A policy ALLOW does not prove delivery, and cannot bypass M2/M3.

Table priorities 70/60/50 identify M2 block/meter and M3 meter within the dynamic
stage; they are **not global OpenFlow priorities**. A static priority 1 DROP
still precedes dynamic protection. System rows explain safety exemption and
forwarding. User-origin rows execute in the M1 static stage; M1 identifies the
original example rule. Dynamic rows cannot be edited or deleted through rule APIs.

Safety is exempt from M2 observation and M2/M3 rate budgets. Successfully delivered
controller-bound safety reports still traverse the original identity parser,
consistency checker and reputation update exactly once; V2V copies do not update
central reputation again. Explicit static safety DROP/METER rules remain allowed
under existing behavior and carry warnings because they can suppress observations
or delay recovery. ALLOW never skips safety parsing.

M2 and M3 recovery is independent. Removing/expiring a dynamic restriction never
removes static rules. Source identity, reputation, budgets and logical flow hits
survive handovers. Provider switches and explicit simulation resets start fresh
run counters while preserving saved rules/settings.

## Counters and the decision inspector

All hits are recorded in `_send` on the actual processing path, not from pulses,
snapshot rendering, hypothetical tests or currently associated vehicle counts.

- Static `match_count`: packets for which that rule was selected. A selected
  ALLOW/METER can subsequently be overridden by M2 DROP. Shadowed rules get no
  selected hits. Static counters restart on edit/toggle and vanish on deletion.
- Dynamic block hits: actual M2-blocked packets. Dynamic meter hits: packets
  reaching evaluation of that budget, including budget-exhausted attempts.
  Static and dynamic hits across rows must not be summed as unique packets.
- System hits: packets passing policy admission toward forwarding/safety delivery,
  before modeled radio/congestion outcomes. They are not reception counts.
- `last_matched` is simulation seconds, null until a hit; zero is a real timestamp.
  Dynamic counters accumulate per logical source/rule until simulation reset,
  and an inactive retained row can show previous hits. `active` describes logical
  installation/enable state, not successful routing or a current packet match.
- No hit count is itself a drop count. Continue using the packet reason totals
  and actual outcomes for loss/rate-limit evidence.

Selecting a vehicle retains position/speed/RSU, actual observed pps, mobility-aware
threshold, M2 stage and M3 trust/band. Expand **Defense decision inspector**:

- **Current victim-UDP preview** evaluates installed policies for a modeled 1024 B
  UDP/9999 packet to the configured victim. It lists matching static rules, meter
  candidates, deciding rule and reason. It does not insert that packet into M2.
- **Latest actual packet decision** records sequence, simulation timestamp,
  traffic/destination, policy action, selected/applied IDs, deciding rule and
  final modeled outcome. It may be safety/telemetry rather than the last flood
  packet; the traffic label makes that explicit. Missing evidence stays missing.

Only one latest decision per actual source is retained. Logical counters are
bounded by the configured 100-rule limit, 36 dynamic IDs and two system IDs.

## Rule warnings and sandbox

**Check draft** validates without installation or persistence. Enabled static
rules receive conservative pairwise duplicate, full-shadow, partial-overlap and
different-action/rate conflict warnings. Node/IP contradictions and unsupported
offered protocols are flagged. Higher static ALLOW can intentionally override a
lower static DROP, but cannot cancel dynamic protection. Warnings do not reject
valid intentional rules. The overview lists at most 256 warnings plus a truncation
notice; a focused draft check examines overlaps for that draft separately.
The analyzer is not a multi-rule union/shadowing theorem prover.

The packet sandbox accepts `source_ip`, `destination_ip`, `protocol`, `src_port`,
`dst_port`, `size` (1–65535 bytes), and optional `rsu`. Omitted ingress uses a known
sender's current association. Unknown IPv4 senders have no modeled reputation
or mobility context; wildcard/IP static rules can still match them. Port 5005
maps to safety only for UDP. Other unsupported UDP ports use generic telemetry
classification for this policy-only preview.

```json
{"source_ip":"10.0.0.7","destination_ip":"10.0.0.2","protocol":"UDP",
 "src_port":40007,"dst_port":9999,"size":1024}
```

The response includes matching static IDs, selected static ID, policy action,
deciding rule, precedence explanation, meter candidates/rate and an explicit
preview scope. It does not forecast a new M2 threshold crossing, token availability,
route, radio loss or actual reception. Packet size is validated metadata; tokens
are never debited by a preview. It does not mutate RNGs, counters, reputation,
detector windows, timeline or settings. Preserving this guarantee is tested against
a serialized fingerprint of the entire engine state excluding its lock.

## Timeline and persistence

The controller retains the newest **180 events**, each with a monotonically
increasing within-run ID, simulation time, origin, optional vehicle, kind,
message and details. Events include scenario activation/recovery, threshold
crossings, M2 transitions/expiry, invalid safety, reputation changes/band transitions,
rule changes and handovers. It is a bounded teaching trace, not a full packet log.

Origin/vehicle/text filters and **Clear displayed history** operate on browser
state only. Clear advances a display watermark; backend events and export remain.
Event IDs distinguish repeated messages at the same simulation timestamp. Reset
or mobility switching clears the browser watermark and controller run history.

Mutations and profile snapshots share the engine lock. A temporary JSON file is
atomically replaced on success. If persistence fails, the controller mutation is
rolled back and HTTP 500 explains it; the previous saved profile remains intact.
Invalid profiles, duplicate IDs and reserved dynamic IDs cannot partially load
new configuration. The supported deployment is one local server/operator; the
file does not provide cross-process transactions or remote multi-user access.

## API additions

| Endpoint | Behavior |
|---|---|
| GET `/api/state` | Existing snapshot plus `flow_table`, `rule_warnings`, `decision_inspector`, `controller_events`, `packet_schema` |
| GET `/api/flows` | Logical rows and bounded warnings |
| GET `/api/events` | Newest bounded timeline and limit |
| POST `/api/rules-analyze` | Validate/check a draft; optional existing ID; read-only |
| POST `/api/policy-preview` | Test hypothetical metadata; read-only |
| Existing rule create/update/toggle/delete | Same endpoints, extended optional matching fields |
| GET `/api/report` | Adds logical flows, latest actual decisions and warnings to the simulated evidence export |

Filters are applied in the browser. All APIs remain local to `127.0.0.1`.

## Demonstrate it

1. Start `.\START_WINDOWS.bat` from `VisualUnified`. On the map inspect V07 and
   expand its defense decisions. Note the lack of actual evidence before packets.
2. Start **Combined attack** with V07/V02; observe the M2 threshold, metering/block
   and M3 reputation separately. Open **SDN Control Center → Simulated flows**.
   Filter M2/M3 and compare policy hits with actual packet reason/drop counters.
3. In Rule Studio create V07 → V02 UDP/9999 DROP at priority 900. **Check draft**,
   read warnings, then save. Static hits increase; M2 stops observing those dropped
   packets. Add a lower ALLOW to demonstrate shadow/conflict warnings; delete it.
4. Test the same packet in **Packet sandbox**. The explicit PREVIEW result changes
   no live counters. Disable the static DROP; dynamic block/meters still apply.
5. Filter the timeline to V07/M3, then **Clear displayed history**. New events
   appear while old controller history remains available in the evidence export.
   Restore normal traffic and observe independent recovery without losing rules.
